# 이미지 재현 진단 로그 PRD

## 배경

문제 사진을 붙여 넣은 뒤 결과가 원본과 다르게 그려져도, 현재 앱에는 어느 단계에서 차이가 생겼는지 사후에 확인할 수 있는 기록이 없다. 콘솔 오류와 마지막 모델 정보만으로는 모델의 장면 해석, 장면 컴파일, 자동 보정, 의미 검증, 캔버스 적용 중 어느 단계가 원인인지 구분하기 어렵다.

## 목표

- 이미지 재현 요청마다 고유한 `traceId`를 부여한다.
- 장면 해석부터 캔버스 적용까지 단계별 산출물과 검증 결과를 한 보고서로 묶는다.
- 새로고침 뒤에도 최근 보고서를 조회할 수 있게 브라우저 로컬 저장소에 제한적으로 보존한다.
- 모든 내부 검사를 통과했더라도 원본 이미지와 결과를 직접 비교하지 않았다면 `source_fidelity_unverified`로 표시한다.
- 원본 이미지, API 키, 인증 토큰, 비밀번호, 전체 사용자 지시문은 진단 기록에 남기지 않는다.

## 사용자 시나리오

1. 사용자가 문제 사진을 붙여 넣거나 업로드한다.
2. 앱이 이미지 준비, 모델 장면 해석, 컴파일, 자동 보정, 검증, 적용 단계를 기록한다.
3. 결과가 잘못되면 개발자는 `window.app.getLastImageDebugTrace()`로 마지막 보고서를 확인한다.
4. 보고서의 `suspectedStage`, 단계별 `errors`, `changes`를 보고 어느 구간부터 산출물이 달라졌는지 좁힌다.
5. 필요하면 `window.app.exportLastImageDebugTrace()`로 민감정보가 제거된 JSON 문자열을 복사해 공유한다.

## 기록 단계

| 단계 | 기록 내용 |
| --- | --- |
| `input_preparation` | 파일 형식·크기, 원본/처리 치수, 자르기·축소 여부 |
| `model_scene` | 모델·응답 ID·시도 번호, 구조화된 장면 결과 |
| `scene_compile` | 컴파일된 작업 목록과 경고 |
| `coverage_validation` | 필수 장면 요소 검사 결과 |
| `quality_enhancement` | 보정 전후 작업 차이 |
| `semantic_validation` | 요청 의미와 작업 목록의 일치 검사 결과 |
| `canvas_apply` | 스키마·참조·의미 검사 및 실제 적용 결과 |

## 보존 및 안전 기준

- 저장 키: `graphA_image_debug_traces_v1`
- 최근 5건만 보존한다.
- 한 보고서는 직렬화 기준 300 KB 이하로 제한한다.
- 객체·배열의 깊이와 항목 수, 문자열 길이를 제한한다.
- `apiKey`, `authorization`, `token`, `password`, `secret`, 이미지 데이터 URL과 원문 지시문 계열 필드는 제거한다.
- `data:image/...;base64,...` 형태의 문자열은 키 이름과 관계없이 제거한다.
- 저장소 사용이 불가능하거나 데이터가 손상되어도 이미지 재현 기능 자체는 계속 동작해야 한다.

## 범위에서 제외하는 것

- 원본 이미지와 렌더링 결과의 자동 시각 비교
- 문제 사진 재현 알고리즘과 프롬프트 변경
- 별도 화면 또는 관리자 대시보드
- 서버·외부 관측 서비스로 로그 전송
- 기존 저장 이미지나 사용자 자료 수집

## 완료 기준

- 성공·검증 실패·API 예외 모두 하나의 종료된 진단 보고서를 남긴다.
- 모델 장면, 컴파일 결과, 보정 결과의 차이를 보고서에서 구분할 수 있다.
- 캔버스 적용 단계의 최초 실패 위치와 오류를 확인할 수 있다.
- 모든 검사 통과 시에도 원본 대조가 없으면 진단 상태가 `source_fidelity_unverified`이다.
- 민감정보 제거, 저장 개수·크기 제한, 손상 복구가 자동 테스트로 검증된다.
- 전체 테스트와 정적 빌드가 통과한다.
